# Financial Tools Service — Architecture

**Status:** proposed, user-approved in principle 2026-10-14. Supersedes the
in-process tool model described in `specs/interfaces.md` §6 for deployment; §6's
Tool Contract shape is unchanged.

**Decision carried forward (do not re-litigate):** convert **all** financial tools
to a platform-owned service. Apps and agents call across a boundary. The platform
holds final authority and owns the record of human approvals.

---

## 1. The principle

Today an app pulls the financial tools into its own process and holds live
references to them. Safety is therefore a property of *each generated app*, and
since apps are generated by an LLM, safety is only as good as whatever happened to
be generated. There is no single place that decides anything, and no way to update
a payment rule once and know it reached everyone.

The inversion: **apps request; the platform decides and acts.**

This yields one structural guarantee worth stating plainly:

> An app cannot grant itself permission to move money.

That is true regardless of what the app contains, because the app never held the
authority. It is a property of the architecture, not of the generated code.

---

## 2. Deployment units

| Unit | Owns | Owns state? | Can move money? | Can approve money moving? |
|---|---|---|---|---|
| **Financial Tools Service** | payment execution, email delivery, ledger, spreadsheets, graph, simulation | **Yes — sole source of truth** | Yes | **Yes** |
| **Intent Authority** | record of human approvals; issuing/validating authorizations | **Yes — sole source of truth** | No | **Yes** |
| **Action Agent** (per app) | deciding what to do next; proposing tool calls | No | No | No |
| **Audit Agent** (per app) | adjudicating proposals against a mandate | No | No | No |
| **Generated App** | UI, workflow, app-specific policy | App-local only | No | No |

Separate containers. Action and audit agents are decoupled from the platform and
from each other. They meet only at the service boundary.

**Intent Authority is logically separate from payment execution** even where
co-deployed: the money-mover cannot approve itself, and the approval authority
cannot move money. It exists as its own boundary so it can be split out without
redesign, and so it can cover other sensitive actions (customer email, shared
record writes), not only payments.

---

## 2b. Two facts about the current system that shape this

**The gate seam is already resolved.** `platform/agent-integration/` makes the
standalone auditor authoritative and treats the in-app gate as a local pre-filter,
which is what §4 rule 1 requires. §4 rule 2 — an app can narrow but never widen —
is already enforced structurally there: the auditor loads a *reviewed manifest
file* rather than generating one from whatever task type the app asks for, so an
app cannot write its own permission slip. This spec extends that property to the
tool boundary; it does not re-decide it.

**Two separate tool populations exist, and they are not unified.** This is the
single largest obstacle to "convert all the tools."

| Population | Tools | Reached by the gated agent loop? |
|---|---|---|
| `fin_tools` (this package) | 12: payments, email, spreadsheets, graph, simulation, intent | **No** |
| `agent_toolkit` (action side) | 2 mocks: `lookup_invoice`, `send_email` | **Yes — it is the default** |

The integration layer's default tool source is the action side's two mocks. So the
financial tools that carry the intent-verification guarantee are not currently on
the path where money-moving decisions get adjudicated. Converting them to a
service is necessary but **not sufficient** — they must also become the tools the
agent loop actually calls, or the guarantee sits beside the system rather than
inside it.

Unifying the two populations is therefore a prerequisite, not a follow-on. The
Tool Contract (§6 of `specs/interfaces.md`) is already the shared shape both sides
describe themselves in, and the integration layer's contract adapter is the
existing translation point — the two differ in how they name the side-effect flag
and how they expose input schemas, which the adapter already absorbs.

---

## 3. What crosses the boundary

**Tool calls:** tool name, arguments, caller identity, and an authorization
reference. The Tool Contract from `specs/interfaces.md` §6 — name, description,
input/output schema, side-effect flag — is the discovery surface, published by the
service. The side-effect flag continues to decide whether a call runs directly or
becomes a proposal.

**Verdicts:** the audit agent's decision on a proposal, with the rule that
produced it.

**Authorizations:** issued by the Intent Authority, presented by the action agent,
validated by the service before settlement. They are bound to exact transaction
parameters — amount, currency, payee — and are single-use with a short lifetime.
Any change to those parameters invalidates the authorization.

**Never crosses:** signing material. Only the Intent Authority holds it. If an
agent can hold it, the agent can mint its own authorization, which defeats the
guarantee entirely. Authorization values themselves are treated as credentials
everywhere they travel or are recorded.

---

## 4. Authority rules

1. **The platform's verdict is final.** An app-local check is a pre-filter: it may
   reject early, cheaply, and with good error messages for whoever is building the
   app. Its approval is not permission.
2. **An app can narrow its agents' authority. It can never widen it.**
3. **Fail closed.** If the service or the Intent Authority cannot be reached, a
   side-effecting call does not proceed. Read-only calls may be served from
   app-local data if the app declares that it may.
4. **No settlement without a validated authorization.** This holds at the service,
   which is the only party that can see both the money and the approval record.
5. **Deterministic decides, probabilistic proposes.** An LLM may draft confirmation
   text or summarise an intent for a human. It never decides whether something is
   authorized.

---

## 5. Adoption order

Conversion is a breaking change to three parties that currently pull tools into
their own process: the action-agent runtime, the audit agent, and the worked
example. Converting service-side only leaves nothing running. The sequence below
keeps the system working at every step.

| Phase | What happens | Broken? |
|---|---|---|
| **0** | Tools available in **both** modes: in-process (today's behaviour, still default) and remote. Same interface either way. | Nothing |
| **1** | **Unify the two tool populations** (§2b) so the gated agent loop reaches the financial tools rather than only the two action-side mocks. The integration layer's contract adapter is the translation point; its self-check is the guard that fails loudly if the two sides drift again. | Nothing |
| **2** | Service deployed; ledger, intent records, idempotency tracking and payer profiles move behind it. Signing material server-side only. | Nothing |
| **3** | Action agent gains a remote client; apps opt in one at a time. | Nothing |
| **4** | Audit agent adjudicates via the service rather than in-process. Local gate stays advisory (already its role). | Nothing |
| **5** | Remote becomes the default for deployed apps; in-process remains for tests and local development. | Nothing |

Phase 0 is what makes everything else safe: **keep an in-process mode**. It
preserves offline testing, keeps local development instant, and means no component
is stranded mid-transition. The audit agent already implements exactly this
pattern — one client interface, three interchangeable transports — and the
integration layer already selects among them, so that is the shape to mirror
rather than invent.

Phase 1 is the one most likely to be skipped and most expensive to skip. A
service boundary around tools nothing calls is architecture theatre: the
"cannot self-authorize" guarantee would be real but would not apply to the agent
loop that actually proposes actions.

**If the build tightens, land Phases 0–2 on payments only.** Payments is where the
guarantee lives and the tool a judge will ask about; the rest is the same pattern
repeated. A complete payments boundary plus the spec beats twelve half-converted
tools.

## 6. Cross-boundary coordination

| Package | What must change | Owner |
|---|---|---|
| `platform/financial-tools/` | dual-mode tools; service; server-side signing material | **mine — no coordination needed** |
| `platform/agent-integration/` | point the loop at the unified financial tools; remote client selection | **mine — no coordination needed** |
| `platform/action-agent-builder/` | in-process `AuditGate` stays narrow-only; tools resolved across the boundary | its agent |
| `platform/audit-agent-builder/` | stop recording authorization values in clear | its agent |
| `entry-point/` examples | call remote tools instead of importing them | its agent |

**One open defect requiring another agent's fix, confirmed still present:** the
audit package's redaction list does not include the authorization field, so a
genuine payment credential reaches the audit log in full when the auditor asks the
owner a question about it. This cannot be fixed by not sending the credential —
rules must inspect it to adjudicate. The fix is upstream: add the field to the
redaction set. Until then, §3's rule that authorization values are credentials
everywhere they travel or are recorded is violated by that path, and it should be
raised with whoever owns `audit-agent-builder` rather than worked around.

This document defines the boundary precisely enough that each party can adopt
independently. It is a coordination artefact, not an instruction to edit their code.

### Market data sits outside this boundary, deliberately

`fin_tools/market_data.py` is a **packaged** adapter, not a managed service behind
this boundary. Three reasons:

- **It carries no trust material.** A market tool cannot move money, cannot issue
  an authorization, and cannot write ledger state — every one is
  `side_effects=False`, and the module never imports `World` or `Payments`. The
  point of this boundary is that signing material lives server-side so an app
  cannot self-authorize (§3, §4). Nothing here needs that guarantee, so routing it
  through the service would add latency and a failure mode for no security gain.
- **It is read-only quote data.** §3 governs what crosses the boundary because
  crossing it is what makes a call adjudicable. A quote has nothing to adjudicate.
- **Failure semantics belong to the app, not the gate.** An unavailable rate must
  surface to the agent as `unavailable` — retryable, nobody decided anything —
  rather than as a gate `rejected`. Keeping it in-process makes that distinction
  direct instead of something the boundary has to preserve on the agent's behalf.

**The cost, stated plainly:** a packaged adapter means every deployed app holds its
own `TUSHARE_TOKEN` and its own quota. A managed API would hold the credential
once, rotate it once, and cache once. If that trade starts to hurt — many apps
against one rate-limited upstream — market data is the first thing that should move
behind this boundary, and `ALLOWED_APIS` is already the seam that would let it: the
same four tools could be served remotely without changing their names or schemas.
Recorded rather than decided, because `specs/decisions.md` still lists
managed-versus-packaged as an open question.

## 7. Consequences to state out loud in the pitch

- **Accountability sits with the platform operator**, not with generated code. A
  judge asking "can you trust AI-generated code with money?" gets a structural
  answer instead of a testing answer.
- **Regulatory change is a one-place change.** Update the payment tool once; every
  agent inherits it, with no drift and no redeployment of apps.
- **Apps become thin and cheap to generate**, which is the point of a
  build-apps-from-a-sentence platform.
- **Cost:** one more boundary to build, deploy, secure and monitor, plus network
  latency on every tool call. Accepted deliberately.
- **Not claimed:** that this makes generated apps correct. It makes them
  *incapable of self-authorizing*, which is a different and more defensible claim.

---

## 8. Not in scope

- Choice of transport protocol and hosting model — mechanism, decided at build time.
- Persistence technology for service state — mechanism.
- Whether the Intent Authority is deployed as its own container or co-located with
  the service behind an internal boundary. Both satisfy §2; the choice is
  operational, not architectural.
- Real money movement, real SCA devices, real payment rails.
